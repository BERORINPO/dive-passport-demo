# 段階 1 の土台: お店の名簿をサーバーに置く（2026-10-27、周 1）

> 計画の時の記録。今の形は spec/architecture.md、置き方は docs/deploy.md。食い違うときはそちらが正しい。古くなった行は「済み」を付けるか書き直してある。

全部を作る計画（B。決定ログ build-all）の段階 1。今の試作は、入れた物がその端末の中（localStorage）だけに残る。
お店の複数の端末と、お客さん・一緒に乗るお店のリンクが、同じ名簿を見られるようにする。

## 決めたこと

- **名簿の正本はサーバー（Cloudflare D1）に置く。** 端末の localStorage は写し（電波が無いときにも開ける）
- **お店の名簿は 1 つの文書として持ち、版の番号で書き込みを守る。** 書く側は「この版を元に直した」（base）を付けて送り、サーバーの版が違えば断って最新を返す（409）。
  画面は、名簿を直す決まり（roster-core.js などの関数）を最新に当て直して送り直す。直す決まりは全部、名簿を受けて新しい名簿を返す関数なので、当て直せる
- **サーバーは画面を信じない。** 受け取った名簿は、画面と同じ js/roster-schema.js で形を確かめ、記録の中身を消し（scrubLog）、保存期間を過ぎた便を消し（purgeExpired）、他のお店のお客さんの健康の答えを外して（holdPartnerHealth）から置く。日付は Worker の時計（日本の日付）
- **お店の Worker の入口は Cloudflare Access だけ（お店のスタッフ）。** お客さんのリンク（/ask・/api/ask）は作った（済み）。Access の無い別の Worker redux-ask（ask.reduxdive.com）が受ける。一緒に乗るお店のリンクはまだ（plan/meibo.md の「乗り合いの本物の形」）
- **お店は 1 つの仕組みで何店でも扱う（済み）。** 下の「お店ごと」。D1 の shops が空のあいだは 1 店（shop = default）で動く

## 口（/api/roster。Access 必須・同じ場所からの呼び出しだけ）

| method | 送る物 | 返す物 |
|---|---|---|
| GET | なし | 200 `{ version, state }`（まだ無ければ `version: 0, state: null`） |
| PUT | `{ base, state }`（JSON、1 MB まで） | 200 `{ version, state }`（サーバーが直した後の名簿）/ 409 `{ error: 'conflict', version, state }`（最新）/ 400 形が合わない / 413 大きすぎる |

- 置いてある名簿が形の検査に落ちたら、渡さずに 500（壊れた物を画面に広げない）
- ログは 1 要求 1 行。道・状態・版・大きさだけ（名簿の中身は出さない）

## 保存の形（D1）

```sql
CREATE TABLE rosters (
  shop TEXT PRIMARY KEY,
  version INTEGER NOT NULL,
  state TEXT NOT NULL,       -- 名簿の JSON（サーバーが確かめて直した後の物）
  updated_at TEXT NOT NULL
);
```

- base が 0 のときは INSERT（同じお店が既にあれば何もしない = 409）、それ以外は `WHERE version = base` の UPDATE。書けた行が 1 つでなければ 409
- D1 の 1 行は 2 MB まで。名簿の本体は 1 MB で止める。済んで 7 日を過ぎた便は、下の「済んだ便を分けて置く」のとおり便ごとの行へ移すので、本体に入るのは先の予約と直近 7 日の分だけ

## お店ごと（2026-10-27）

1 つの仕組みで何店でも扱う。D1 の `shops`（worker/migrations/0003_shops.sql）が、お店の一覧（id・名前・スタッフのメール・予約フォームのサイト・予約メールの受け口のアドレス）。
- スタッフ: Access でログインしたメールを一覧で引き、そのお店の名簿（rosters.shop = id）だけを読み書きする。どのお店にもいなければ 403。名簿のお店の名前は一覧の名前にそろえる
- サイトの予約: 送ってきたサイト（origin）でお店を決める。Turnstile もそのお店のサイトの hostname だけを通す。1 日の件数はお店ごと
- 届いたメール: 宛先（封筒の To）でお店を決め、送り主はそのお店の senders で確かめる（ドメインを置いたあと）
- 1 日の上限は、お店ごと（サイト 30・メール 30）と全店あわせて（サイト 300・メール 60）の両方で数える
- 一覧の行が 1 つでも形が合わなければ止める（503）。一覧から消したお店は、Cron もリンクも動かさない（ザクのレビュー 2026-10-27）
- お客さんのリンク: 鍵と一緒に置いたお店（ask_links.shop）の名簿を読む
- Cron: 名簿があるお店を全部回る（1 店が失敗してもほかは止めない）
- 一覧が空（表が無い D1 も）のあいだは、今までどおり 1 店（default）で動く
- 判定は worker/shop-core.mjs（core）、読み出しは worker/shop-db.mjs。テストは test/shops.test.mjs

お店を足す（今は D1 のコンソールで。画面は後で）。`node tools/shop.mjs add --id … --name … --member …` が値を確かめて 1 文を作る（remove・keep-sample も）:
```sql
INSERT INTO shops (id, name, members, sites, inbox, senders) VALUES ('shop-a', 'A ダイブ', '["staff@example.com"]', '["https://shop-a.example.com"]', '', '[]');
```
- 1 店目を足した時点で、一覧が空でなくなるので、今の見本（default）の名簿はどのスタッフからも見えなくなる。見本を残すなら、見本のお店の行も足し、id を default にする
- スタッフは Access の Policy と ALLOWED_EMAILS にも足す（入口は Access のまま）

## 済んだ便を分けて置く（2026-10-27。ジンのレビュー CRITICAL 3）

名簿を 1 お店 1 行に置いたままだと、1 日 5 人のお店で 3〜4 か月で 1 MB の上限に届き、無料の枠では 1 回の書き込みの CPU も 10 ms に近づく。
そこで、**済んで 7 日を過ぎた便を、便ごとに 1 行へ移す**。名簿の本体の大きさは、1 年分の予約でなく、先の予約の数で決まる。

- 分ける決まり: worker/past-core.mjs の splitPast（core）。便・その予約・人・予定・送った連絡・その便の記録を 1 つにする。お店全体の記録（AI の読み取りなど、id が空）は 1 日分を 1 つにする（part = `log:YYYY-MM-DD`）
- 7 日は、済んだ予定と連絡の本文を外す日（js/roster-auto.js の compactPast）と同じ。7 日までは、本体で直せる（中止の後の連絡・記録の直し）
- 分けるのはサーバーが名簿を書くときだけ（checkPut。画面の PUT も、Cron・予約フォーム・届いたメールの changeRoster も同じ道）。読むとき（GET）は分けない（分けた物を書く前に画面へ渡すと、次の書き込みで消えるため）
- D1: `roster_past`（worker/migrations/0004_roster_past.sql）。名簿の本体と同じ batch（1 つの transaction）で書く。済んだ便の行は「版がまだ base のとき」だけ足す。別の端末に負けた書き込みは、本体も済んだ便も書かない。行が多くても 1 文（json_each）
- 一度書いた行は上書きしない（DO NOTHING）。便を最初に移すのは、その便の最新を持つ書き込み（版で守る）なので、後から同じ便が届くのは古い写しだけ。行の名前は便が `trip:<id>`、記録が `log:YYYY-MM-DD@v<書いた版>`（遅れて届いた記録で前の記録を消さない。同じ中身は読むときに 1 つにする。ジンのレビュー 2026-10-27）
- 端末側: 開き直したときの「送れていなかった名簿まるごと」は、その間にサーバーの版が進んでいたら当てず、端末の名簿を別の場所に残す（js/core.js の replaceWith。古い写しで別の端末の直しを消さない）
- 作成の日から 1 年（keep_until）を過ぎた行は、次に済んだ便を移すときに消す（Cron が動けば Cron でも）。読む口も渡さない
- 人が大きく消える書き込みの守り（shrinkProblem）は、今の名簿からも済んだ便を除いてから比べる（分けた日の書き込みを事故と見ない）
- 読む口: `GET /api/roster/past?from=YYYY-MM-DD&to=YYYY-MM-DD`（Access の内。93 日まで、今日まで、400 行まで）。お店はログインしたメールで決める。返すのは済んだ便だけの 1 つの名簿（読むだけ）と、形が合わずに外した行の数（skipped。黙って消さない）
- 画面: 予約の一覧の「済んだ便を見る（7 日より前）」→ 月ごとの一覧 → 条例の名簿の紙（印刷・PDF）。直す所は無い。サーバーを使わない版（GitHub Pages）には出さない（端末の中の便は今までどおり 1 年で消える）
- テスト: test/past.test.mjs（SQL は node:sqlite でも流す）と test/sync-client.test.mjs

まだのこと:
- 済んだ便を直す道（例: 済んだ後に保険の会社から問い合わせがあって、記録を足したい）。要るとなったら、1 便ずつ本体に戻す道を足す
- 済んだ便の名簿を印刷・書き出したときの記録（今は本体の便だけが logOutput を残す）
- 先の予約が多いお店（1 日 30 人を 2 か月先まで、など）は、本体だけでも 1 MB に近づく。Workers Paid では CPU の上限は外れる。足りなくなったら、先の便も便ごとの行にする

## 名簿の形の版と、端末のお店（2026-10-27。ジンのレビュー HIGH 7・8）

- 形の版（HIGH 7）: 名簿・便・予約・人・予定・連絡には v が付く。形を変えるときは js/roster-schema.js の VERSION を 1 上げ、MIGRATIONS に「前の版 → 次の版」の関数を 1 つ足す。
  読む所（端末の loadRoster・別のタブの保存・サーバーの readStored・済んだ便の行）は、検査の前に upgradeState を通す。古い版の画面から届いた名簿は、サーバーが上げずに 426 で断る
  （上げると、画面が知らない新しい欄を消して書くため）。画面は送るのを止め、端末の名簿を別の場所に残して「読み込み直して」と出す。サーバーの名簿が画面より新しい版のときも同じ
- 端末のお店（HIGH 8）: /api/roster はどのお店の名簿か（shop）も返す。端末はつないだときのお店を覚え（redux-roster-v1-sync の shop）、
  ログインしたお店が違えば、端末の名簿は送らず別の場所に残して、そのお店の名簿にする（他のお店の名簿に混ぜない）。覚えていない端末の名簿は default の物とみなす
  開いたままの画面で別のお店の人がログインし直したときのため、画面は PUT に shop を付け、サーバーはログインから決めたお店と違えば 409（error: shop）で断る。
  画面は送るのも取り込むのも止め、端末の名簿を別の場所に残して「読み込み直して」と出す（shop を付けない前の版の画面は今までどおり）
- 開き直したときの「送れていなかった名簿まるごと」は、その間にサーバーの版が進んでいたら当てない（js/core.js の replaceWith）
- まだのこと（ジン・ザクのレビュー LOW）: shop を付けない前の版の画面の PUT は通している（2 店目を足す前に、shop を必ず付けさせる）。お店が変わったときに退避した前のお店の名簿は、端末に最長 1 年残る（共有端末なら期限を短くするか、お店ごとに分ける）

## 重さ・やり直し・テストの本物さ（2026-10-27。ジンのレビュー MEDIUM 9〜12）

- 端末の退避（MEDIUM 9）: 読めなかった名簿の退避（redux-roster-v1-broken-）は新しい 3 つまで。名簿の本体を保存できない（容量切れ）ときは、その退避から古い順に消して書き直す（本体はサーバーにもある）。
  送れなかった直しの退避（redux-roster-v1-kept-）は端末にしか無いので、数の上限も容量切れの整理もかけない（1 年で消すのは同じ）。残せなかったら画面に sync-lost と出す（ジンの再レビュー）
- 送る量（MEDIUM 10）: 8 KB を超える名簿の PUT は gzip で縮めて送る（content-encoding: gzip）。Worker は中身が gzip の形のときだけほどき、ほどいた後も 1 MB で止める。受け取る名簿は Cloudflare が縮めて返す
- やり直し（MEDIUM 10）: サーバーの書き込み（changeRoster）は、ぶつかったら少し間をずらして 5 回まで（前は 3 回ですぐ 503）
- 連絡の二重送信（MEDIUM 10）: 送る前に印（why = sending:<時刻>#<この回>）を付けて書き、書けた物だけを送る。1 回に印を付けるのは 10 件まで（途中で止まったときに「分からない」になる幅を小さくする）。送った後に結果を書けなかった物は、もう一度は送らず、30 分後に「送れたか分からない」（failed / maybe-sent）にして画面に出す
- テストの本物さ（MEDIUM 11）: test/d1-sql.test.mjs が、同じ操作を fakeD1 と本物の SQLite（node:sqlite、migrations を全部流した表）に流して答えを比べる。adapter の SQL が全部 1 回は流れたかも確かめ、handler から SQLite につないで通しでも動かす
- 長い行（MEDIUM 12）: 180 字を超える行の数を、ファイルごとに test/long-lines.json より増やさない（arch で検査）。今は 52 行。直したら json を下げる。説明は日本語のまま（作るのも引き継ぐのも日本語のチーム）

- 送り直し（2026-10-28）: 「送れたか分からない」の連絡は、書類の自動化の画面（画面 10）で、お店がお客さんに確かめてから「届いていた」か「送り直す」を選ぶ。送り直しは元の連絡に resent の印を付けて、新しい連絡を 1 つだけ足す（js/roster-auto.js の resend。2 回押しても・Cron が重なっても 1 通、test/auto-worker.test.mjs）

## 毎日の控えと警報（2026-10-28。ジンのレビュー CRITICAL 2）

名簿が消えても誰も気付けず、D1 の巻き戻しは 30 日だけだった。
- Cron が 1 日 1 回（今日の控えがあれば何もしない）、お店ごとに名簿の本体をそのまま Workers KV（BACKUP）に置く。1 年残す。D1 とは別の保存場所
- 済んだ便の行は、最後に写した所（pastcursor: 移した時刻と part）の続きから全部写す（Cron を動かす前の行や、止まっていた間の行も）。1 行 1 回。消える日（keep_until）まで残す
- 警報: 直近 7 日の控えのうち人がいちばん多い日より、5 人より多く、かつ 3 割より多く減ったら（済んだ便に移った人は除く）。名簿の行が消えた・読めない形になった・0 人になったときは数に関係なく。運営（ALERT_TO）にメールし、KV にも残す（同じ日は 1 回）。知らせには数だけで名前を入れない。Cron は一覧のお店（一覧が空なら default）も回るので、行が消えたお店にも気付く
- 戻す: tools/restore.mjs が控えを形の検査にかけ、D1 の API に送る本文を作る（手順は docs/deploy.md の 8）。控えのお店と違うお店へは戻さない。戻す前に書き出した今の名簿の版でだけ書き、戻すと消える予約と人の数を出す。戻すと版が進むので、開いている画面も戻った名簿になる（ジンのレビュー 2026-10-28）
- 決まりは worker/backup-core.mjs（core）、つなぐのは worker/backup.mjs、テストは test/backup.test.mjs
- 済み（2026-10-28）: Workers Paid にして Cron が動き、メールも送れる。警報は secret ALERT_TO が入っていればメールでも送る（KV にも残る）

## まだ決めていないこと

- **（済み: 済んだ便は roster_past へ便ごとに移す。上の「済んだ便を分けて置く」）名簿が 1 MB を超えたときの分け方（便ごと・月ごと）。** 手元で測ると、見本の乗り合い便（30 人）で 54 KB だった。1 MB は約 550 人分で、1 年に数千人を案内する店には足りない。本物の店で使う前（段階 1 の終わりまで）に、便ごとに分けて持つ形へ直す
- （済み: 毎日 KV に 1 年。上の「毎日の控えと警報」）バックアップ（D1 の Time Travel は 30 日。1 年保存の名簿には別の写しが要るか）
- （済み: shops の inbox と senders）複数のお店のときの、メールとお店の対応表の置き場所
